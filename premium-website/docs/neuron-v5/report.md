# neuron-v5: передача эстафеты и завершение скролла

Ветка `feat/neuron-finale`. Baseline, метод и стенд — `baseline.md`; драйвер —
`tools/finale.mjs`; сырые данные — `data/`, кадры — `shots/`. Всё, что ниже, снято той
же сессией Chrome 152 headless-new на Apple M3, что и baseline.

---

## Что сделано

Финал v4 был собран правильно по замыслу и имел пять дефектов исполнения; все пять
воспроизведены в baseline цифрами и кадрами, потом починены — не подгонкой чисел, а
приведением к одной системе отсчёта и одному скаляру передачи. Одна гипотеза промпта
(1.7, демпфер) замером **не подтвердилась**, и λ не тронута; вместо этого решена
обратная проблема, которую показал тот же замер.

| # | Дефект | Было (baseline) | Стало |
|---|---|---|---|
| 1.1 | Коробка в долях `100svh`, кадр — по высоте канваса | при коробке на 10 % ниже канваса диаграмма уезжает на **54–61 px** | **0 px** на трёх соотношениях, с «адресной строкой» и без |
| 1.2 | Лента не умеет исчезать | на пути вверх 45 кадров лента поверх нейрона; гаснет скачком 1.0 за кадр на `p=5` | лента гаснет там же, где разгорается сома; скачок за кадр ≤ 0.28 при быстром скролле вверх, 0 кадров ленты поверх нейрона |
| 1.4 | Камера едет во время передачи | камера на `z=8.6` только к `p≈7.04`, перо зажглось на 6.86 | плоскость диаграммы держится на 8.6 перед камерой: кадр верен на всём отрезке |

## Критерии приёмки

### 1. Метки на строках сетки при любой высоте вьюпорта

`data/after-align.json`, `data/after-align-squeeze.json`,
`shots/after-align-squeeze-{16x9,4x3,9x19.5}.jpg`.

| | коробка = канвас | коробка на 10 % ниже канваса (было → стало) |
|---|---|---|
| 16:9 | Δ 0 / 0 / 0 / 0 px | Δtop **57.1 → 0** px |
| 4:3 | 0 | **53.9 → 0** |
| 9:19.5 | 0 | **61.1 → 0** |

Выбран путь **(б)** из промпта: замер остаётся относительно липкой коробки, но
возвращает CSS-пиксели, а не доли — `finaleFrame.ts`, `boxFromRects()`. По горизонтали
координаты берутся прямо во вьюпорте (по x ничего не едет), по вертикали — как смещение
от верха контейнера, который приклеен `top: 0` всю главу (и это теперь проверяет тест).
Высота контейнера в расчёт не входит вообще, так что «свободный член» `h_канваса − svh`
исчез по построению. Путь (а) — мерить `.rig` относительно вьюпорта — потребовал бы
гарантировать момент, когда контейнер приклеен; (б) от этого момента не зависит.

Инвариант проверяем: `lib/finale-frame.test.ts`, блок «коробка и кадр — в одной
единице», на чистых функциях без DOM. Пиксель, возвращённый из кадра на экран, обязан
совпасть с пикселем коробки при любой высоте контейнера (810, 729, 900, и когда он ещё не
приклеен) и любой высоте канваса. **Проверено, что тест падает:** временно вернул
вертикаль долей высоты контейнера, как в v4 —

```
× пиксель коробки не зависит от высоты липкого контейнера
AssertionError: expected 616.17 to be close to 554.55, received difference is 61.6
```

— 61.6 px, ровно масштаб дефекта на 9:19.5 в baseline. Вернул — 16 тестов зелёные.

Как эмулировано: у headless Chrome нет динамической панели, `svh == innerHeight`
всегда. Поэтому липкой коробке принудительно дана `height: 90vh` (`SQUEEZE=0.9` в
драйвере), канвас — во весь вьюпорт. Это та же геометрия, но не реальный телефон; на
реальном не проверялось.

### 2. Раскадровка `p = 6.0 → 8.0`

`shots/{baseline,after}-story-p6_0…p8_0-16x9.jpg`, `data/{baseline,after}-story.json`.
Столбец `p` — фактическая позиция режиссёра (о разнице с запрошенной — `baseline.md`,
«подводные камни»).

| p | было: перо / лента / камера z | стало: перо / лента / камера z / плоскость z |
|---|---|---|
| 6.00 | 0 / 0 / 5.60 | 0 / 0 / 5.60 / −3.00 |
| 6.26 | 0 / 0 / 6.38 | 0 / 0 / 6.38 / −2.22 — нейрон тает и летит к началу ленты |
| 6.46 | 0 / 0 / 6.98 | 0 / 0 / 6.98 / −1.62 — нейрон уже точка на месте пера |
| 6.56 | 0 / 0 / 7.28 | **0.35** / 0 / 7.28 / −1.32 — передача началась |
| 6.66 | 0 / 0 / 7.58 | **1.00** / 0 / 7.58 / −1.02 — перо зажглось, уголёк погас |
| 6.76 | 0 / 0 / 7.88 | 1 / **0.66** (progress 0.056) — запись пошла |
| 6.86 | **0.55** / 0 / 8.18 | 1 / 1 (0.13) |
| 6.96 | 1 / **0.18** / 8.48 | 1 / 1 (0.21) |
| 7.04 | 1 / **1.00** / **8.60** | 1 / 1 (0.29) / 8.60 / 0 |
| 7.10 → 7.50 | запись 0.24 → 0.93 | запись 0.39 → 0.95 |
| 7.61 | дописано | дописано |
| 8.01 | стоп-кадр | стоп-кадр — тот же |

Все три события теперь на своих местах и разнесены: полёт к перу занимает половину
отрезка, передача — 0.15 главы **при уже стоящем на месте нейроне**, запись начинается
на 0.04 главы позже конца передачи. В baseline камера доезжала до финальной оптики
позже, чем зажигалось перо; теперь плоскость диаграммы стоит на `FINALE.CAMERA_Z`
перед камерой всю дорогу (`planeZ` в `Neuron.tsx`), и её экранный прямоугольник верен
с первого кадра отрезка. Нейрон стартует из центра экрана (`neuron.position` вспышки —
`[0, 0, −0.8]`), цель лежит в плоскости диаграммы, камера на оси: проекция точки
`s·T` — это `s·T·k(z)`, направление на экране постоянно, траектория прямая; на кадрах
`p6_3`, `p6_4` (стало) блоб нейрона стоит ровно на калибровочном импульсе, где через
две десятых зажжётся перо.

Два светящихся точки: в кадрах `p6_5…p6_7` перо разгорается ровно там, где стоит
сжатый до 0.09→0.04 уголёк — одна точка. Нейрон и полностью прочерченная лента
одновременно: во всех четырёх трассах **0 кадров** с непрозрачностью ленты > 0.5 при
`p < 6.5` (было 45 в `updown`).

### 3. Вниз → вверх до `#services` → снова вниз

`data/after-trace-updown.json`, `data/after-trace-replay.json`.

| | было | стало |
|---|---|---|
| лента поверх вернувшегося нейрона (кадров) | 45 | **0** |
| непрозрачность ленты на `p = 5.0` при движении вверх | 1.0 → 0 скачком | уже 0 |
| макс. скачок непрозрачности за кадр (весь сценарий) | **1.000** | 0.284 |
| скачок сетки за кадр | 0.06 | 0.06 |

Механика: непрозрачность ленты ведётся тем же `handoff`, что и перо
(`uOpacity = handoff × clamp01(drawn × 12)`), — третий вариант из предложенных в промпте.
Обоснование: чернила — след пера, и они видны ровно тогда, когда перо в руках прибора;
отдельная величина по главам дублировала бы `handoff`, а демпфер на `drawn` ломал бы
монотонность прочерченности, которую v4 просил не пересматривать — она не тронута
(`drawn` по-прежнему максимум достигнутого, сброс ниже `climax-build` остался, но
теперь случается при уже нулевой непрозрачности). На пути вверх лента гаснет там же,
где разгорается уголёк сомы: передача идёт в обратную сторону.

0.284 за кадр — это фейд длиной 0.15 главы при скролле вверх со скоростью 1.33 главы/с
(4 главы за 3 с) — семь кадров. Назад потолка скорости нет сознательно (ниже, 1.7).
При обычной прокрутке вверх фейд занимает 15–30 кадров.

Повторный заход (`replay`, третий отрезок — обратно вниз из `#outro-draw`): `progress`
1.02 во всех кадрах, `pen` возвращается 0.03 → 1.0 плавно, `penSize` 50.8…59.6 px —
пульс запаркованного пера виден, `handoff` в нуле не залипает. Это **допустимый
минимум** из 1.3, и выбран он сознательно: необратимость записи — решение v4, а
любое движение пера без чернил (пойти назад по уже записанному) читалось бы как
ошибка прибора. Второй заход — статичный прибор с дышащим пером. Если владелец
захочет большего (например, перо на повторе слегка ярче), это одна строка в
`exit-verdict.eeg.head`.

### 5. Подсветка бумаги впереди пера

`shots/{baseline,after}-draw-16x9.jpg`. Было: перо на 0.37 ширины квада, светится
полоса 0.10…0.33 позади него. Стало: полоса впереди пера. `materials/eeg.ts` получил
юниформ `uPenX` — доля ШИРИНЫ квада, `(penPoint.x + GRID_W/2) / GRID_W`, зажатая в
[0, 1]; берётся из той же точки кривой, по которой ставится спрайт пера, аллокаций
нет. Дуга и ширина расходятся не постоянно, а знакопеременно (дуга/ширина = 2.12;
−0.13 перед QRS, +0.13 после), поэтому и после QRS полоса теперь впереди. Верхняя
граница базы (`smoothstep(0.72, 0.95, uPenX)`) — где по ширине квада заканчивается
запись, чтобы у дописанной диаграммы база выходила на тот же максимум, что раньше
(0.87), и стоп-кадр не изменился.

## Про 1.7 и почему λ не тронута

Промпт просил менять демпфер только по подтверждённому замеру. Замер (`baseline.md`,
трассы):

* при обычной прокрутке отставание `p` от `targetP` ≤ 0.118 главы и исчезает в
  момент остановки (Δp = 0.001) — это ровно постоянная времени λ = 6 (167 мс), и
  сцена не «едет после отпускания». Как дефект не подтверждается;
* при флике отставание есть (0.75 главы, 850 мс догона), но дефект там **обратный**:
  демпфер при далёкой цели разгоняет `p` до ~20 глав/с, и передача пролетает за один
  кадр. Ужесточать λ — значит проскакивать ещё сильнее; гасить демпфер по `still` —
  значит на десктопе с колесом получить перо, идущее ступенями по 10 % ленты на каждый
  щелчок.

Поэтому вместо λ введён **потолок скорости таймлайна вперёд** внутри финала
(`DIRECTOR.FINALE_MAX_SPEED = 2` главы/с, от `climax-flash` до `exit-verdict`,
`useScrollDirector.ts`). На обычной прокрутке `p` идёт ≤ 1 главы/с, и потолок не
срабатывает — трасса `slow` после правки даёт то же отставание 0.117. На флике он даёт
передаче 42 кадра вместо одного. Назад потолка нет: на пути вверх лента гаснет и нейрон
собирается обратно, смотреть на это не обязательно, а сцена, отстающая от скролла уже
на хиро, была бы заметнее любого пропущенного фейда.

## Что было сломано по дороге

**1. Первый шаг раскадровки уезжал на 180 px.** Ленивые картинки врачей и клиники
догружаются при первом проходе и удлиняют документ; драйвер считал метки до этого.
Прогрев (до низа и обратно) перед раскадровкой и трассами. Побочное наблюдение:
режиссёр после этого сдвига метки **не перемеряет** — ResizeObserver стоит на `body`,
а высота body от подгрузки картинок в карточках фиксированной высоты не меняется.
Расхождение ≈ 0.1 главы в финале, к теме задачи не относится, но записано.

**2. Прыжок `scrollTo(from)` внутри `scrollRun` попадал в трассу как отставание 4.9
главы.** Теперь драйвер ставит скролл на старт отрезка и ждёт 1.2 с до записи.

**3. `remeasure` мерила коробку дважды.** Первая версия читала `getBoundingClientRect`
внутри функционального `setState` — это и побочный эффект в апдейтере, и лишние два
чтения. Замер вынесен до `setBox`.

**4. Проба идемпотентности кадра в `after-resize.json` сравнила разные `p`.** Проба
ждёт 30 кадров после `scrollTo`, а с потолком скорости этого не хватает, чтобы `p`
дошёл до стоп-кадра: в «до» `group.z = 3.71` (камера ещё едет), в «после» 0. `x`,
`y`, `scale` — то, что не зависит от `p`, — совпадают до последнего знака; вывод об
идемпотентности стоит на них.

## Компромиссы и что не сделано

**Флик догоняется 1.4 с вместо 0.85.** Это прямое следствие потолка скорости: сцена
обязана показать передачу и запись, а скролл уже стоит на футере. Считаю это ценой,
которую стоит платить — самописец, дописывающий линию после того, как вы отпустили
колесо, читается как прибор; нейрон, который никогда не превращается в перо, потому
что вы прокрутили быстро, — как сломанный финал. Но это **решение, которое владелец
может пересмотреть одним числом** (`FINALE_MAX_SPEED`: 3 → передача ~30 кадров,
догон ~1 с).

**Фейд ленты на пути вверх при быстром скролле — 7 кадров.** Потолка назад нет
сознательно (см. 1.7). При обычном скролле вверх фейд 15–30 кадров.

**Повторный заход — минимум из 1.3.** Прибор статичен, перо пульсирует (±8 %,
1.2 с). Необратимость записи сохранена, «оживления» больше этого нет.

**`npm run lint` красный по причинам вне задачи** — см. критерий 8.

**Проверки только в headless Chrome, реального устройства не было.** «Адресная
строка» эмулирована принудительной высотой липкой коробки; соотношения сторон —
`Emulation.setDeviceMetricsOverride`; тиры `mid`/`low` форсированы `?tier=`.

**Изменение стоимости кадра не измеримо на этом стенде** — разброс между сериями
(±1.5–2 п.п.) больше порога приёмки (+1 п.п.). Две серии «после» приведены целиком.

**1.8 сделано в объёме, который просил промпт, не больше.** Пересчёт кадра диаграммы
теперь без ре-рендера React (замер в rAF, `setBox` с порогом четверть пикселя вместо
`1e-4` в долях — тот отсекал шум, но в долях вьюпорта, где `1e-4` = 0.08 px; новый
порог в пикселях и тестируется), `refresh` ScrollTrigger идёт через тот же rAF, что и
`resize`. Счётчик чтений раскладки на один `resize` не изменился (13): десять меток
режиссёра и две коробки читались в одном rAF и до этого, третий пересчёт (`refresh`)
в синтетическом `resize` не участвует. В пачке из пяти `resize` пять чтений
приходятся на безымянный `div` — это не код сцены (ScrollTrigger или R3F), и он
уйдёт с `ignoreMobileResize` в мобильном промпте. Полное лечение пачек адресной
строки — там же, как и договаривались.

**Один коммит на все блоки кода.** Кадр (1.1), ритм (1.4/1.5), лента (1.2/1.3),
подсветка (1.6) и потолок (1.7) живут в одной функции `applyState` и проверяются одним
тестовым файлом; промежуточные состояния (например, новые окна без `planeZ`) собрались
бы, но были бы неверны по смыслу и не проходили бы тест ритма. Как и в v4, разбивать
задним числом на несобирающиеся или неверные коммиты не стал. Baseline и драйвер —
отдельным коммитом, отчёт и данные «после» — отдельным.
